## Context

`timeGrid()` (shared by `week()` and `day()`) renders a times column and then one `.bc-cal-col` per day or resource;
each column holds an `<ol class="bc-cal-body bc-cal-rows-N bc-cal-slot-S">` whose `<li class="bc-cal-event">` items
are placed with `bc-cal-row-R` / `bc-cal-span-K` (grid rows) and, when they overlap, `bc-cal-lanes-L bc-cal-lane-I`
(twelve sub-columns). Events link to their `url`; overflow and outside-hours events go to `<details>` in the header.

`basecoat-dnd.js` grid mode works on **one** `[data-dnd-grid]` element: items carry `data-dnd-row/col/span`, the
script swaps the classes listed in `data-dnd-classes` (`row`, `col`, `span` maps), uses `data-dnd-slot` cells as
pointer targets, `data-dnd-resize` handles for the span, flags overlaps with `data-dnd-collision`, and fires the
cancelable `basecoat:move` / `basecoat:resize` (and POSTs to `data-endpoint` when set). Its keyboard model and
announcements already exist and are tested in `tests/js/dnd.test.js`.

## Goals / Non-Goals

**Goals:**
- Interactive week and day views on top of the existing dnd grid mode, opt-in, with no change to today's output.
- Slot-level values (date, start, end, resource) in the events, so apps don't translate indexes.
- Steps of 5, 10, 15, 20, 30 and 60 minutes.

**Non-Goals:**
- Persistence, confirmation UI, month view changes, recurring or multi-day events.

## Decisions

### 1. One 2D grid only in interactive mode

When `interactive` is set, the body becomes a single `<div class="bc-cal-grid-body" data-dnd-grid ...>` with
`grid-template-columns: repeat(C, var(--bc-cal-col))` (class `bc-cal-cols-C`) and the rows of today's `.bc-cal-body`;
column headers stay in their own header row above it (same widths), and the times column stays to the left. Items get
`bc-cal-c-K` (column) besides the row and span classes; `data-dnd-classes` lists `row` → `bc-cal-row-*`, `col` →
`bc-cal-c-*`, `span` → `bc-cal-span-*`. With `interactive` unset, `timeGrid()` keeps its current per-column markup.

*Alternative considered:* teach `basecoat-dnd.js` to move items between sibling grids. Rejected: it duplicates
collision, keyboard and text-binding logic that grid mode already has, and it adds a second contract to document.

### 2. Overlaps inside a cell: lane width classes

In one grid an item can't also sit in twelve sub-columns of its day. Overlapping events keep their lane computed on
the server and get width classes (`bc-cal-lanes-L bc-cal-lane-I` mapped to `width: calc(100% / L)` and an
inline-start margin via classes, not inline style). After a client-side move, lanes may be stale; that's acceptable
because the move is either cancelled (apps confirming on the server) or followed by a re-render; overlaps are still
flagged with `data-dnd-collision` and announced.

### 3. Slots

With `interactive.slots`, every row × column cell is rendered as an empty
`<a class="bc-cal-slot" data-dnd-slot data-dnd-row data-dnd-col data-dnd-label="Tuesday 24 November 10:00, Luis A."
href="…">` (link from `slotUrl`; a cell with `slotUrl` returning `null` is a plain `<span data-dnd-slot>`, a drop
target but not a link). Slots sit under the events (lower stacking order) so clicking an event never hits a slot.
Every cell gets a slot, also those under an event: grid mode looks the slot up by row and column for pointer drops
and for the `{slot}` announcement, so a missing cell would drop on a neighbour and announce "Row r, column c".
Without `interactive.slots`, cells are plain `<span data-dnd-slot>` only when `move` is on (drop targets).

### 4. Values in the events

The grid carries `data-dnd-row-text` (the slot boundaries, `HH:MM`, rows + 1 entries) and `data-dnd-col-text` (column
labels), plus new `data-dnd-col-values` (dates `Y-m-d` in the week, resource keys in the day) and `data-calendar-date`.
`basecoat-dnd.js` adds `detail.slot = {start, end, column}` built from those lists when present (generic: `column` is
the value of `data-dnd-col-values`), and the helper documents how it maps to date/resource. No calendar-specific code
in the script.

### 5. Locked events and steps

`'locked' => true` on an event renders it without `data-dnd-item` / handle (still a link, still announced as normal).
`SLOTS` becomes `[5, 10, 15, 20, 30, 60]`; `ROWS`/`ROW`/`SPAN` maps and the CSS grow to 288 entries, generated by a
small script in `bin/` into `basecoat-calendar.css` (no runtime cost). `bc-cal-slot-5/10/20` backgrounds draw the hour
line strong and the step lines soft, like 15 and 30 today.

### 6. Event attributes

`eventAttributes` (`fn (array $event): array`) merges attributes into each event's `<a>` (refusing `on*` and `style`
keys, like `data-dnd-attr`), so apps can add `hx-*` or menu-trigger hooks without overriding protected methods.

## Implementation notes (adjustments made while building it)

- Markup: `<div class="bc-cal-board bc-cal-cols-N">` holds `<div class="bc-cal-heads">` (one `.bc-cal-head` per
  column, same `bc-cal-name` spans and ids as read-only), `<div class="bc-cal-alldays">` (one `ul.bc-cal-allday`
  per column, only when there are all-day events) and the grid `<div class="bc-cal-grid-body bc-cal-rows-R
  bc-cal-slot-S" data-dnd-grid …>`. `bc-cal-cols-N` sets `--bc-cal-n`, used for `repeat(N, minmax(0, 1fr))` in the
  three rows and for the board width (`N × --bc-cal-col`), so the columns line up and have a definite width.
- Events are `<div class="bc-cal-event …">` grid items; the event link carries `data-dnd-handle` (one tab stop,
  as the month chips) and, when draggable, its times are `<span data-dnd-text="start">` / `"end"` so they follow
  a move. Items carry `data-id` (the event id) and `data-dnd-label` (the title).
- Events come before the slots in the DOM (tab order: events first) and stack above them with `z-index`.
  Slot links also get `aria-label` (same text as `data-dnd-label`).
- `interactive` takes only `move`, `resize`, `slots` (others throw); `resize` without `move` throws (grid mode
  cannot resize an item it does not drag); `slots` without a callable `slotUrl` throws; at most 32 columns.
- `slotUrl` gets `null` as resource in the week, for "Unassigned" and in a day without resources; the day
  without resources has `data-dnd-col-values='[""]'`.
- `eventAttributes` receives the event as the app passed it (its own keys included); `on*`, `style` and
  `href` keys and `null` / `false` values are dropped. It also applies in read-only mode and to the events
  listed in the header.
- `basecoat-dnd.js` also adds `slot` to the endpoint POST payload (same object as `detail.slot`).
- `.bc-cal-grid-body>.bc-cal-event[data-dnd-collision]` only shows the collision outline on the dragged event
  (lanes overlap by design).
- The read-only body moved into `columnsHtml()`; `board()` / `boardEvent()` render the interactive one.

## Risks / Trade-offs

- [Bigger CSS (288-row maps)] → generated once; still a few KB gzipped; only loaded with the calendar.
- [Two renderers in `timeGrid()`] → share the event placement (`lanes()`, `events()`) and test both outputs; the
  read-only one has a byte-for-byte regression test.
- [Touch scrolling vs dragging] → items and handles use `data-dnd-touch="press"` (250 ms long press), as month chips.
- [Stale lanes after a client move] → documented; apps re-render after saving.

## Migration Plan

Minor release (new options only). Consumers opt in by passing `interactive`; nothing else changes. Rollback: stop
passing the option.
